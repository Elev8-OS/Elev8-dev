# workflow
- When asked to "check/explore a feature" with no specifics (or asked "apa lagi celahnya" — what other gaps remain), proactively map the whole feature end-to-end (feature files, mount points, data, tests, wiring) and surface anomalies (e.g. wrong handler wired to a button, dead config, promised-but-unimplemented features, missing UI triggers, data-integrity risks) as a prioritized list ranked by business impact, with a recommendation and an offer to fix. Expect iterative rounds: the user keeps asking for fresh gap passes until satisfied. Confidence: 0.82
- Push to GitHub after completing each feature chunk. Confidence: 0.88
- Update CLAUDE.md alongside pushes to keep project context current. Confidence: 0.92
- Commit first, then push (`git commit` → `git push`). Confidence: 0.70
- Check git status (uncommitted/untracked) before pushing. Confidence: 0.85
- Brainstorm and discuss design before implementation. Confidence: 0.75
- Use test selectors such as stable `data-testid` attributes and accessibility state attributes like `aria-pressed` for interactive controls. Confidence: 0.85
- Prefer test-driven implementation with an explicit RED → GREEN loop for feature work. Confidence: 0.85
- During verification, separate failures caused by repository/environment baseline issues from regressions introduced by the current work, and report both clearly. Confidence: 0.88
- Prefer scoped local test runs when the repository's full test discovery includes generated or worktree tests; still run the full suite when practical to detect regressions. Confidence: 0.82
- When full-suite test discovery picks up stale sub-agent worktrees (`.claude/worktrees/**`) and causes mass failures, fix the root cause by excluding them in the vitest config (`exclude: ['**/.claude/worktrees/**']`) rather than deleting the worktrees or working around them — the worktrees may hold the user's in-progress work. Confidence: 0.6
- Treat focused tests, typecheck diagnostics filtered to touched files, lint, and code review as acceptable manual-flow evidence when the dev server is unstable or cannot boot reliably. Confidence: 0.78
- Review the whole branch against its base and inspect the final diff before declaring work merge-ready. Confidence: 0.82
- Commit follow-up fixes separately with focused conventional commit messages rather than silently amending prior feature commits. Confidence: 0.75
- Exception: when fixing CI/lint failures on a still-unmerged feature branch right before merging, prefer `git commit --amend` + `git push --force-with-lease` over a separate fix commit — keeps the PR history clean and avoids polluting main with a "fix lint" commit. Confidence: 0.82
- When "merge" is requested on a feature branch with an open PR, check CI status first; if lint/typecheck is failing, fix the issues, amend + force-push, then merge via `gh pr merge --merge --delete-branch-remote`. Confidence: 0.85
- Prefer scoped lint runs on only the changed files (e.g. `pnpm exec eslint <changed-files>`) over the full project lint when the full lint is too slow — then run the scoped re-lint to confirm fixes. Confidence: 0.78
- Prefer discovering and fixing missing exports or typecheck regressions uncovered during final verification before finalizing a feature. Confidence: 0.86
- Use `NODE_ENV=test` explicitly for local Vitest runs when the test environment otherwise alters Vue Test Utils behavior or emit capture. Confidence: 0.78
- Model data at the granularity the end user actually selects/redeems, not at a parent/aggregate level. Example: when a "Spa" service has multiple items (1hr, 2hr, body scrub), the picker must let the operator pick specific items — picking the whole service is wrong because the unit of redemption is the item. Confidence: 0.88
- When explaining requirements, prefers concrete real-world examples (e.g. "spa have 1 hour, 2 hours") over abstract spec terminology. Worth asking for or providing an example when intent is ambiguous. Confidence: 0.72
- Exclude auto-managed files (e.g. taste files, untracked local scratch files) from git commits; only stage files explicitly related to the feature being shipped. Confidence: 0.85
- Use a dedicated feature branch with conventional `feat(scope):` naming (e.g. `feat/promo-free-upsell-item-selection`) for non-trivial changes before pushing. Confidence: 0.80
- When opening a PR, mirror the commit message structure and include a dedicated "Verification" section listing the typecheck/lint/test commands that were run. Confidence: 0.82
- After running typecheck on a large project, filter the output to only the touched files (e.g. `vue-tsc --noEmit 2>&1 | grep -iE "ListingPicker|..."`) to separate regressions introduced by the current change from pre-existing baseline errors — then explicitly state that no new errors were found. Confidence: 0.85
- When asked to move/relocate a feature across modules, use `ask_user_question` with concrete placement options (each with a short preview) before touching code — even when the task feels straightforward, placement decisions have lasting structural impact. Confidence: 0.85
- After first implementation of a UI move, do a follow-up visual/scope review pass and ask another clarifying question if the result needs a second iteration (e.g. layout tightening, prop additions) rather than silently refactoring. Confidence: 0.78
- When reusing a full-page list/table component inside a smaller context (sheet tab, popover, card), prefer adding a `compact` boolean prop to the existing component over rewriting an inline version — keeps a single source of truth and lets the original use site stay unchanged when the prop defaults to `false`. Confidence: 0.85
- When a bulk/throttled test exceeds the default test timeout (e.g. 50-item bulk sync with per-item network delay), reduce the fixture size to ~10 items rather than raising the timeout — keeps the suite fast while still verifying the throttle pipeline. Confidence: 0.80
- For health-state integrations: model three discrete states (`connected` / `needs_attention` / `disconnected`) with a separate `flagNeedsAttention(reason)` / `clearNeedsAttention()` / `reconnect(key)` API rather than overloading `disconnect()` — preserves the user's data while flagging the failure for Admin action. Confidence: 0.82
- When seeding domain data (e.g. listings, bookings) that should plug into a third-party integration's mock fixtures, cross-reference guest names / IDs / revenue values between the new domain data and the integration's existing seed data so the end-to-end demo flow remains consistent. Confidence: 0.82
- Standard endpoint cadence at the end of a feature chunk: user asks to push → commit + push to GitHub branch → user says "yes PR" → open the PR → user says "merge" → merge PR (after CI green) + delete the remote branch. Don't volunteer intermediate previews unless asked. Confidence: 0.85
- When `pnpm install` skips ignored build scripts needed by the toolchain (esbuild, @parcel/watcher, vue-demi, maplibre-gl, etc.), don't rely on interactive `pnpm approve-builds` in the agent shell — set `onlyBuiltDependencies` non-interactively via `pnpm config set --location=project onlyBuiltDependencies "[...]"` (writes to project `.npmrc`/`pnpm-workspace.yaml`), then run `pnpm rebuild` to compile the native binaries. Confidence: 0.82
- When a background dev server exits immediately with code 1 and an empty log, re-run the command in the foreground to capture the actual error output before diagnosing. Confidence: 0.72
- When the environment's Node version doesn't match the project's `engines` (e.g. system Node v25 vs required 22.x), don't block on it — proceed if it works (treat as a warning), but flag the mismatch to the user and suggest a version manager (e.g. nvm-windows) for full compatibility. Confidence: 0.68
- When a documented/mocked feature needs a "real" version, implement the code first and update the PRD/doc afterwards to reflect the actual implementation (user chose "implement first, PRD follows"). Confidence: 0.65
- When a design choice carries a data-integrity risk (e.g. one shared sync flag across integrations), re-ask the question with a recommendation even if the user already picked the simpler option — the user will revise when shown the tradeoff. Confidence: 0.6
- When `git pull` is blocked by local uncommitted changes, preserve the user's work and git state: `git stash push` (with a descriptive message like `wip-before-pull`) → `git pull` → `git stash pop`; then confirm the user's real source changes were restored and don't commit anything on the user's behalf — the working tree should reflect the pre-pull state plus conflict resolutions, not new commits. Confidence: 0.74
- When merge conflicts appear in auto-managed `.commandcode/` files (settings allowlists, taste learnings) and are purely additive, resolve by keeping both sides (merge the upstream and local entries) rather than discarding either; afterwards grep for leftover conflict markers before dropping the stash entry. Confidence: 0.7
- When the user hits an error/validation message and asks what it means (e.g. "apa artinya" for "Ownership for listing ... would exceed 100%"), first trace the exact message string in the code and read the enforcing logic (e.g. `validateOwnership()` in `useOwners.ts`) before answering; then explain the plain-language meaning, the rule/flow behind it (e.g. the 2-pass ownership-percentage validation), concrete fixes, and cite file:line references. Explain the error rather than jumping into code changes unless asked to fix. Confidence: 0.65
- When the user reports a bug in a terse Indonesian sentence with no repro steps (e.g. "bug gabisa klik add another"), don't ask for clarification upfront — investigate autonomously: run the related tests first, and if they pass, reproduce in a real browser (start the dev server + drive it with browser automation) to observe the actual DOM/console behavior and root-cause before changing code. Confidence: 0.65
- When a component wraps shadcn inputs that use `useVModel(..., { passive: true })`, Vue Test Utils `setValue`/`trigger` on the mounted component may not produce `update:modelValue` emits, so direct-mount tests can't capture state changes. Drive the scenario through the full dialog flow instead (mount the dialog, navigate to the step, dispatch native input/change events on `document.body` elements) — that path is proven to work. Confidence: 0.6
- When verifying stateful form behavior in a real browser, drive inputs and assert values via native DOM events through `eval` (set `.value`, dispatch `input`/`change` with bubbles, then read values back), because `agent-browser fill`/`snapshot` can silently no-op or omit values when element refs shift or inputs sit inside dialogs. Confidence: 0.55
