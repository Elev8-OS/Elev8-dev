# ui-patterns
- Avatar/identity chips should NOT be monochrome brand-primary (`bg-primary/10 text-primary`, which reads as a flat yellow/amber wash) — the user explicitly said "i dont like the avatar color". The accepted fix for entity avatars (e.g. owners in Users → Owners) is DETERMINISTIC per-name coloring: a fixed palette of distinct hues (sky, emerald, violet, amber, rose, cyan, indigo, lime) each as `bg-{color}-500/10 text-{color}-700 dark:text-{color}-300`, assigned by hashing the entity's name (`hash * 31 + charCode` mod palette length) so every entity gets a stable, recognisable color with no manual assignment. Only sweep the specific entity context the user pointed at (owners) — leave other contexts (users, guests, tenants) that intentionally keep their own style alone unless the user asks. When the user DOES ask ("buat di tab upsell juga" — "also make it on the upsell tab"), scope expands to every other tab/surface where the same owner/persona avatars render, so the avatar treatment stays consistent across the whole app rather than only the first-weaponed surface. Confidence: 0.7

Confidence: 0.9
- SelectTrigger inside table cells must use `w-full` to fill the container instead of hugging content width — but `w-full` alone is NOT enough: the shadcn-vue `Select` root is renderless and is not itself a flex item, so a bare `w-full` trigger only fills the Select's natural (content-derived) width. That makes the field width differ across rows when option text lengths differ and pushes a sibling action button out of view (user-reported bug: "dropdown fieldnya ukurannya ngga sama, jadi ngga keliatan button cancelnya" — dropdown sizes differ so the unmap/cancel button was clipped by the table's overflow-hidden). The accepted pattern: wrap the `Select` in a `<div class="min-w-0 flex-1">` inside a fixed-width flex column (`flex w-[240px] shrink-0 items-center gap-1.5`), keep the sibling action button `shrink-0`, and don't let `overflow-hidden` on the table clip controls — the trigger then fills the same space in every row regardless of option length and the action button always stays visible. Confidence: 0.75

- For domain computation/base settings where several components can contribute to a formula (e.g. which revenue components form a commission base, which items are included in an amount), prefer a CHECKBOX multi-select over a single binary toggle — the user explicitly wants to "pilih sesuka dia" (pick as they please) which components apply, rather than a coarse A/B switch. The checkbox set replaces the toggle; the frame-setting option becomes "none/all selected", and an empty selection means the base is unmodified (e.g. 0 deductions = full Gross). When introducing such a configurable set, give each unchecked item a visible check/uncheck control (icon square/check-square or checkbox) and keep the surrounding computed/label surfaces derived from the full selection, not just the binary state.
