# communication
- Always respond in English, even when the user writes in Indonesian. Confidence: 0.95
- The user gives terse UI-change directives in Indonesian shorthand (e.g. "booking history masukin ke cardnya" — "put booking history into its card"; "munculin info adult berapa child infant berapa" — "show the adult/child/infant counts"), often without naming the exact file or section; the assistant is expected to locate the target, pick the most sensible structural interpretation (e.g. CardHeader title + table body, with the child table dropping its own Card wrapper so cards don't nest), implement it, and commit — without asking clarifying questions. Confidence: 0.65
- For UI changes, the user often conveys the desired design by attaching a reference screenshot plus a short sentence in Indonesian (e.g. "untuk cleaning event cardnya kaya di gambar", "buat cleaning card eventnya tambahin handle by extrasauber, ini pngnya") rather than writing detailed written specs. Treat the screenshot as the source of truth and read it via the vision tool before touching code — this includes extracting brand colors, taglines, and logo styling from the image. Confidence: 0.85
- After completing a UI feature (or a bug fix), proactively state where the user can see it (exact route/page) and how to reproduce it (e.g. "Refresh http://localhost:3000/reservations, buka reservasi, klik ikon pensil di header") — the user will otherwise ask "ceknya dimana" ("where do I check it?"). Offering to seed mock/demo data so the change is visible without manual setup is welcomed. Confidence: 0.65
- When the user phrases a reference-screenshot request as "buat kaya gini tapi lebih kreative" ("make it like this but more creative"), treat the image as inspiration to be enhanced, not a 1:1 template — keep the reference's core elements (ID/status chips, OTA logo, guest avatar + party size, property thumbnail, check-in/out with night count) and layer on creative enrichments (photo hero banner with gradient overlay, notes card, icon bubbles, price breakdown) while keeping previously-requested conventions (e.g. listing links stay black). Confidence: 0.7
- When the user pastes raw text content as the reference for what to display — analytics/stats layouts (labels, numbers, ordering) or actual data content like a booking note ("tambahin reservation notenya kaya ini" + pasted note text) — treat the pasted content as the source of truth and mirror its labels, structure, and wording exactly in the implementation (the exact "** THIS RESERVATION HAS BEEN PRE-PAID ** ... BOOKING NOTE : ..." text was seeded and rendered verbatim, emphasis markers included). Confidence: 0.7
- During design reviews/brainstorming, the user approves presented sections with terse affirmatives ("1", "ya", "yes to all", "start", "goo" — a typo for "go") and expects the assistant to proceed with the recommended/default option — a bare "ya" to a section that contains an open sub-question (e.g. dialog vs. sheet for reservation detail) means "you decide, go with your recommended default", not a request to re-ask; a bare "start"/"goo" after a written spec means "approved — move to the next phase" (e.g. write the implementation plan). Confidence: 0.85
- The user can point at the exact UI element to fix by pasting its code comment/marker or raw HTML markup from the source (e.g. `<!-- Status chip (editable) -->` + "ini" = "this one"; or a pasted `<div>...</div>` block of a section header + "hapus ini") instead of describing the element — treat the pasted markup as the target and infer the desired change from the surrounding context rather than asking what they mean. Confidence: 0.7
- Boundary case to the "implement terse directives without asking" preference: when a terse Indonesian request uses a vague umbrella term that could map to several distinct features (e.g. "buat setting untuk reservation" — could mean edit info, housekeeping, smart lock, upsell, or status/payment settings), ask ONE clarifying question with concrete labeled multi-select options before building — the user engaged with the option list and picked "Edit info reservasi" (the Recommended option) — rather than guessing. Specific one-line capability requests (e.g. "bisa add dan delete cleaning dari sana") are still implemented directly without asking. Confidence: 0.6
- When the user provides a formal, numbered flow spec in Indonesian (e.g. "Flow 1: Tenant Connect Email (Setup — one-time)" describing entry point, options, steps, pending state, and verified behavior), treat it as the authoritative product spec: map the existing implementation against each spec point, close the gaps (tenant-slug default address, optional records, pending-state fallback, verified fan-out), update tests, and browser-verify — without asking clarifying questions. This is the structured-spec variant of the terse-directive pattern. Confidence: 0.6
- When the assistant surfaces open requirement questions with recommended defaults (e.g. "is inbound email in Phase 1 or not?"), the user resolves them with a terse Indonesian directive that names the requirement directly — "email masuk juga harus support" ("inbound email must also be supported") — instead of picking the numbered recommendation or answering "ya". Treat the directive as the scope decision and implement the full scope (receive pipeline, unmatched-sender edge cases, connection-state gating, tests, browser verification) without re-asking. Confidence: 0.6
