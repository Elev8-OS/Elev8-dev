### Listing Module (`app/components/listings/`)

#### Data + Types (`app/components/listings/data/listings.ts`)
- `Listing` type with `photos: string[]`, `unitType: 'single' | 'multi'`, `aiSchedule: AiSchedule`, plus `stats`, `pricing`, `bookings`, `blockedDates`, `reviews`, `maintenance`
- **AI schedule (HostBuddy concept)**:
  - `AiSchedule` = `{ always: boolean (24/7), days: DayHours[] (7, Mon→Sun), dateOverrides: DateOverride[] }`
  - `DayHours` = `{ enabled, slots: TimeSlot[], activeFor: OverrideAudience[] }` — multiple time ranges per day
  - `TimeSlot` = `{ id, start, end }` (24h "HH:MM")
  - `DateOverride` = `{ id, startDate, startTime, endDate, endTime, activeFor }` — date RANGES that override the weekly schedule
  - `OverrideAudience` = `'future' | 'current' | 'inquiry'`
  - `alwaysOn()` factory builds a 24/7 default schedule
- `ListingStats`, `ListingPricing` (nightlyRate/fees/discounts/seasonalRates), `Booking`, `Review`, `MaintenanceTask`, `ListingMaintenance`
- `Unit` — `{ id, name, identifier?, status?, otaConnected? }` (no longer carries `aiStatus` — moved to `UnitType`)
- `UnitType` — `{ id, name, identifier?, description?, quantity, maxAdults/Children/Infants, bedrooms, bathrooms, beds[], photos[], pricing: UnitTypePricing, aiStatus?: 'active' | 'paused' | 'not_set', units: Unit[] }`. `UnitType.aiStatus` is only the fallback for rooms without their own (older data); ElevAI is set per room (`Unit.aiStatus`)
- `UnitTypePricing` — `{ currency, ratePlans: RatePlan[], offerings: RatePlanOffering[], lengthOfStayDiscounts: LengthOfStayDiscount[], fees: Fee[] }` — supports **multiple rate plans per room type** (e.g., Standard, Weekly, Monthly)
- `RatePlan` — Channex-style: `{ id, name, title, sellMode: 'per_room'|'per_person', rateMode: 'manual'|'derived'|'auto'|'cascade', currency, childrenFee, infantFee, maxStay[], minStayArrival[], minStayThrough[], closedToArrival[], closedToDeparture[], stopSell[], options: RatePlanOption[], parentRatePlanId, inherit*, autoRateSettings, mealType, taxSetId?, isBase }` — exactly one plan per `UnitType` has `isBase: true` and cannot be deleted. Use `createRatePlan()` for defaults, `ratePlanNightlyRate(rp)` / `ratePlanMaxOccupancy(rp)` to read the primary option (no more `pricePerNight`/`pricePerAdditionalGuest`)
- `RatePlanOffering` — derived from base (fixed/percent adjustment); not the same as a RatePlan
- `ListingDocument`, `ListingResources` (documents, basics, sops, topicsToAvoid (deprecated), avoidTopics, propertyUpsells, fieldConfig)
- `FieldConfig` = `{ stages: ReservationStage[] }` — per-field config stored in `listing.resources.fieldConfig[fieldKey]`
- `ReservationStage` = `'future' | 'inquiry_past' | 'current'`
- Reactive: `listings` uses `ref<Listing[]>` — mutations use `listings.value[index] = updated`
- Helper exports: `allTags`, `allLocations`, `allProperties`, `allOtas` (computed)
- Mock data: 16 listings with Unsplash photos (lst-1 has rich mock data + custom schedule; rest use `alwaysOn()` + defaults)

#### Page (`app/pages/listings/[id]/index.vue`)
- 9-tab layout: Overview | Pricing | Revenue | Calendar | Reviews | Maintenance | Guest Guide | Channels | Settings (Channels = `channels/ListingChannelsTab.vue`, see `channels.md`) (Revenue = per-room revenue engine settings, see `revenue-settings.md`; no Protection tab: damage protection is set once for the tenant in Settings, see `damage-protection.md`). `?tab=<value>` opens a tab, and a link to it from inside the page switches the tab
- **Custom tabs** (`listings/data/listing-custom-tabs.ts`, `Listing.customTabs`, read via `listingCustomTabs`): after Settings, one tab per entry (globe icon, the name) and an **Add tab** button at the end of the tab list. `ListingCustomTabDialog.vue` takes a name (max 30) and a link; `normalizeTabUrl` adds `https://` when missing and rejects anything not http(s) (no `javascript:` in the frame). The tab shows `ListingCustomTabFrame.vue`: toolbar (name, host, reload, open in new tab, menu with Edit / Move left / Move right / Remove, remove asks first), then a sandboxed `iframe`. ⚠️ A site that refuses framing (`X-Frame-Options` / CSP `frame-ancestors`, e.g. most Google pages other than published or `/preview` links) cannot be detected from a cross-origin frame (the browser still fires `load`), so the frame first asks `GET /api/frame-check?url=` (`server/utils/frame-check.ts`: reads the site's `X-Frame-Options` and CSP `frame-ancestors` against the dashboard origin, never fetches private/localhost hosts, 5s timeout). `embeddable: false` swaps the frame for a "can't be shown here" card with Open in new tab; `null` (check failed) keeps the frame, with "Open in new tab" in the toolbar and a footer line, and a frame with no `load` after 6s gets the same pointer. The link placeholder is a plain `https://` (not a Google Docs link, since Docs in edit mode is often refused). Tab values are `custom:<id>`, so `?tab=custom:<id>` opens one. Per listing, not shared across listings.

- ⚠️ **Cleaning checklists, three levels** (`cleaning/data/cleaning-step-templates.ts`): for a (listing, cleaning type) the job's checklist is (1) the listing's override in `maintenance.cleaningTemplates` (a template id, or `LISTING_CUSTOM_STEPS` = `'custom'` for the listing's own `cleaningSteps`), else (2) the **company default** for the type (`typeDefaults` in `useCleaningStepTemplates`, localStorage `elev8-cleaning-type-defaults-v1`), else (3) none: that type cannot be scheduled. One resolver, `resolveListingChecklist(maintenance, type, library)`, returns `{ origin: 'default' | 'template' | 'custom', template, name, sections }`; a deleted or empty override falls back to the default. Job sources map through `cleaningTemplateTypeFor` (legacy `manual` → `custom`, `checkout` → `check_out`). Defaults and overrides are LIVE references; a job copies the resolved steps AND `checklistName` when created (`cleaningChecklistSnapshot`), so template edits reach new jobs only. **A new tenant is active at once**: `SEED_CLEANING_TYPE_DEFAULTS` (check-out Villa standard, daily and mid-stay Daily refresh, custom Deep clean), and `completeTypeDefaults` keeps every type on an existing template (stored default, else the seed default, else the first template). **Lazy migration**: a listing with no `cleaningTemplates` field whose own steps differ from every template is treated as custom for every type (`listingChecklistOverrides`); own steps equal to a template (the seeds) follow the defaults. Always write overrides through `withListingOverride` (starts from the effective overrides), never from `{}`. Seed: lst-1 overrides check-out with Deep clean.

- ⚠️ **Daily routine** (`useCleaningJobs().syncRoutineCleanings`): a listing whose schedule (`scheduleFor`: its own, else the company default) is `daily` is cleaned EVERY day, booked or not, `ROUTINE_HORIZON_DAYS` (14) ahead, one job per listing per day typed by `routineDayType` (`cleaning-link.ts`): `daily` with a guest in, `check_out` on departure day (wins over an arrival), `vacant` ("Vacant upkeep", new job source + template `cst-vacant`) when empty, but only on days `schedule.vacant` makes due (`vacantCleaningDue` in `reservations/data/cleaning-schedule.ts`: `weekdays` | `every_n_days` counted from the listing's last cleaning of any kind | `every_day` | `never`; absent = `DEFAULT_VACANT_CLEANING`, Monday and Thursday); blocks, inquiries and cancellations are not stays. Jobs carry `routine: true`; only routine jobs not yet started are retyped (checklist re-copied) or removed. A day with a non-routine job (by hand, or a reservation's customised schedule) is left to it. Deleted routine days are remembered (`routineSkips`) and a cancelled one is not refilled. A booking on a routine listing gets no schedule of its own (`useReservationsModule`); `createFromCheckout` reuses that day's check-out job. Run by `plugins/cleaning-routine.client.ts` on load, on any change to reservations, listings, the company schedule or checklists, and hourly (tests call it directly with a fixed `today`). Multi-unit listings get one routine job for the whole listing.

#### Listing Status System
- `Listing.status?: 'active' | 'inactive'` — listing-level status
- `Listing.aiStatus: 'active' | 'paused' | 'not_set'` — listing-level AI status (used for single-unit + as a derived aggregate for multi-unit)
- `Unit.status?: 'active' | 'inactive'` — per-unit status
- `Unit.otaConnected?: string[]` — per-unit OTA override (falls back to listing OTA)
- `Listing.otaConnected` is written only by `useChannels` (see `docs/claude/channels.md`); logos come from `otaIcon()` in `components/channels/data/channels.ts`
- `Unit.aiStatus?: 'active' | 'paused' | 'not_set'`: **ElevAI is set per room** (HostBuddy treats every room as a property). A room without its own value falls back to `UnitType.aiStatus` (older data), else on. Read it only through `roomAiStatus` / `roomsWithAi` / `aiActiveRooms` and write it through `setRoomAi` / `setListingAi` (`listing-ai-status.ts`). Turning a room off (expand row) pauses its ElevAI and turning it on resumes it; the listing's own switch (`ListingSingleToggle`) does the same for every room.
- **Multi-unit logic**: property status derived from units — all inactive = property inactive
- **AI aggregation** (multi-unit only): for the table's AI Status column, `ListingAiStatusCell` aggregates from `unitTypes[]` — any unit type active → "Active", all unit types paused → "Paused", otherwise falls back to `listing.aiStatus`
- **Deactivate cascade**: turning off listing/unit pauses AI at the unit-type level (and updates the listing-level `aiStatus` derived aggregate)
- **`ListingExpandRow.vue`**: a multi-unit listing's room types and rooms rendered as ROWS of the listings table, under the listing and lined up with its columns (it takes the row's visible `columnIds` and fills only its own cells): a room-type row (name and room count in the name column, "ElevAI on N of M" for its rooms in the AI Status column) and a row per room (its on/off switch in the status column, the room name indented in the name column with an Inactive badge, its **ElevAI on/off** switch in the AI Status column via `setRoomAi`, a check in each channel column it sells on). The listing's own switch already turns every room on or off, so there is no extra "all rooms" control. Not a panel inside the name cell (that stretched the row and floated the other columns). Toasts on each toggle.
- **Listings table sorting** (2026-10-18): a header click cycles ascending, descending, off (same as Reservations and Tasks; `toggleSort` in `pages/listings/index.vue`) with a chevron on the sorted column. Status toggle, Tags, Amenities and actions are not sortable (`enableSorting: false`). Sorting is saved in views: `SavedView.sorting` / `ViewState.sorting` (`{ id, desc }[]`, compared in `isDirty`; a view saved before it existed reads as the default order through `normalize`).
- **`ListingSingleToggle.vue`** — handles both single and multi-unit toggle logic; for multi-unit it writes `unitType.aiStatus` (not per-unit); shows `toast.info/success` on activate/deactivate
- **`ListingRowActions.vue`** — "Activate/Deactivate Listing" in dropdown; implemented with spread mutation
